### 内存：为什么不阻塞、下一步怎么定位

- 口径：`footprint` 统计的是进程物理占用，含可回收（reclaimable / purgeable）内存；本次 WebContent 304 MB 里 193 MB 标为可回收，内存紧张时系统会收回，不可回收部分约 111 MB。主进程和 GPU 进程本次没有单独记录，所以「整体」既不能判通过，也不能判不通过。
- 场景是压力场景（23 图 + 10 种代码 + 2 MB JSON 树 + 二维码依次打开），不是日常闲置；机器也不是方案规定的 M1 / 8 GB。
- 定位步骤（R10 开头做，不改功能）：
  1. 分别记录 DevBar 主进程、WebContent、GPU 进程的 `footprint`，三个场景：刚启动闲置、日常（剪贴板 + 一段 JSON）、压力；每个场景再在 `memory_pressure -S -l warn` 后复测，记录可回收部分是否真的回收。
  2. 查缓存上限：Mermaid SVG 缓存（64 张）、Shiki 高亮器与语言、2 MB JSON 树 DOM、长图离屏 WKWebView 是否用完即释放。
  3. 面板隐藏一段时间后释放大对象（树 DOM、离屏快照视图），并走已有的 `memory.flush` 路径；对比优化前后数据。
  4. 在 M1 / 8 GB 复测后才判定是否达标。
