### 复核时额外发现（不阻塞，并入 T0.2 处理）

自己又试了几种写法，以下仍未拦住或有误报：

| 写法 | 结果 | 期望 |
|---|---|---|
| `globalThis.JSON.parse(…)`、`window.JSON.stringify(…)` | 未报错 | 报错 |
| `const J = JSON; J.parse(…)` | 未报错 | 报错 |
| `(0, eval)("…")` | 未报错 | 报错 |
| `const f = fetch; f(…)` | 未报错 | 报错 |
| `db.fetch()`、`db.eval()`（普通对象上的同名方法） | **误报** | 不报错 |

处理意见（T0.2 一并改，T0.2 本来就要改这份 lint 配置）：

1. **`src/tools/`、`src/tree/` 下直接禁止出现 `JSON` 这个标识符**（包括 `globalThis.JSON`、`window.JSON`、`self.JSON`）。lossless-json 用不到全局 `JSON`，整体禁掉比逐个写法拦截更简单可靠，别名、解构、方法引用都自然覆盖。
2. `eval`、`Function`、`fetch`、`XMLHttpRequest`、`WebSocket`、`EventSource`：**只在标识符本身或 `window` / `globalThis` / `self` 的属性上时报错**，普通对象的同名方法不报；**被引用（不只是被调用）也报错**，覆盖 `const f = fetch`、`(0, eval)` 这类写法。
3. 以上每一行都加进 `Web/tests/eslint-rules.test.ts`。

说明：lint 只是防止**无意**误用的护栏，不必追求拦住所有刻意绕过。联网另有 CSP 和内容拦截规则两道防线（规格 §5.4），JSON 无损另有 §9.5 的无损链路测试兜底。
