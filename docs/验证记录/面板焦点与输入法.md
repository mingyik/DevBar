## 2. ⌘V / ⌘C / ⌘X 不可用：原因判断（待 R7 修复后验证）

**以下是推断的原因，不是已证实的结论**，要等 R7 修复后看快捷键是否恢复来验证。

- 代码事实：`Sources/DevBar` 中没有设置 `NSApp.mainMenu`，也没有「编辑」菜单。
- 推断：macOS 上 ⌘V、⌘C、⌘X 通常通过「编辑」菜单里「粘贴 / 拷贝 / 剪切」菜单项的快捷键，向第一响应者发送 `paste:` / `copy:` / `cut:`；没有这些菜单项，按键就没有去处。
- 与观察一致的旁证：⌘Z、⌘A 正常（CodeMirror 的键位表在网页里直接处理这两个键，不经过菜单）；右键菜单「粘贴」正常（说明粘贴功能本身可用）。
- **「缺少编辑菜单是唯一原因」是待 R7 修复后验证的判断**，目前不能排除其他因素。

修复方向（供 R7 实现者选择，修复后都要复测第 1 节第 3–8 项）：

| 方案 | 做法 | 说明 |
|---|---|---|
| A. 在面板里转发 | 在 `DevBarPanel.performKeyEquivalent` 中识别 ⌘V / ⌘C / ⌘X（以及 ⇧⌘Z 重做），用 `NSApp.sendAction` 把 `paste:` / `copy:` / `cut:` 发给第一响应者 | 只影响面板内 |
| B. 加隐藏的主菜单 | 启动时设置 `NSApp.mainMenu`，包含「编辑」子菜单 | 第 3 节实测打开面板后 `NSApp.isActive` 为真，DevBar 自己的主菜单可能会处理快捷键；但仍需实测，并确认 ⌘Z / ⇧⌘Z 不会被菜单抢走而绕过 CodeMirror 的撤销历史 |

R7 修复后还要确认：其他应用在前台时，⌘V 粘贴进的是 DevBar 面板而不是那个应用。

## 3. 补测：打开面板后 DevBar 是否被激活（R6 返工）

用自检入口自动测（`T1.4运行时安全.md` 第 1 节的运行方式，观察项「其他应用在前台时打开面板后的激活状态」）：先收起面板并把 Finder 切到前台，再调用 `PanelController.show` 打开面板。连续运行两次，结果一致：

| 项 | 打开面板前 | 打开面板后 |
|---|---|---|
| `NSApp.isActive`（DevBar） | `false` | **`true`** |
| `NSWorkspace.shared.frontmostApplication` | `com.apple.finder` | `com.apple.finder` |
| 面板是否为 key window | — | 是 |

结论（实测）：**打开面板后 DevBar 被激活了**（`NSApp.isActive` 为真），但系统记录的最前台应用（菜单栏的拥有者）仍是 Finder。这与第 1 节第 10 项「菜单栏仍显示原应用」的观察一致，也说明那一项不能用来证明「没有激活」。

限制：这是自检里用 `NSRunningApplication.activate()` 把 Finder 切到前台、再由代码打开面板测得的，不是用户按 ⌃⌥D 的真实路径；两者都走 `PanelController.show`，但触发方式不同。

## 4. 关于「改用 .titled 或临时激活应用」

规格 V1 要求在有问题时对比「改用 `.titled` 隐藏标题栏」与「临时激活应用（`NSApp.activate`）」。本次输入法、焦点、全屏都正常；第 3 节说明现有实现**已经**在打开面板时激活了应用。快捷键问题按第 2 节的判断与面板类型无关，**不建议为此改面板类型**；该判断同样待 R7 修复后验证。
