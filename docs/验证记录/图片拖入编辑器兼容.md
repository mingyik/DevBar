# T2.5 图片拖入编辑器与路径回退

分支：main。需求方报告剪贴板图片拖到 Codex 输入框失败，并要求图片不被支持时至少可提供路径。

## 做了什么

- `ClipboardDragFile.swift`：图片拖出同时提供原始图片数据、现存临时文件 URL、路径纯文本和原有文件承诺。优先使用已有 PNG 数据，否则保留原始图片格式。纯文本和已有多文件条目的拖出流程保持不变。
- 图片和文件 URL 混合的截图也从图片数据生成拖出文件，不再依赖原保存路径是否仍存在；仅改变拖拽表示，不改历史或系统剪贴板。
- 图片拖拽中的纯文本表示使用导出文件路径（覆盖随图片携带的说明文本）；图片原始字节保持不变。目标应用决定采用哪种表示，不能强制不接收拖放的输入框插入内容。
- 临时文件存放于系统临时目录的 `DevBar-ImageDrags`，随机文件名；松手后不立即删除，避免接收方延后读取失败。每个进程首次生成图片拖出文件时，清理此目录中超过 24 小时的本应用文件。路径不是永久保存位置。创建失败时回退到原有数据拖出。

## 问题依据

旧图片文件承诺提供者没有发布真实文件 URL；带原保存路径的截图则直接跳过该提供者。新增回归测试在修改前无法通过 NSURL 读取到文件 URL；修改后可以读取文件及原始图片。文件承诺与文件 URL 是两种不同的接收协议，Apple 示例明确区分了它们：
https://developer.apple.com/documentation/appkit/supporting-drag-and-drop-through-file-promises

尚未据此证明 Codex 内部一定使用某种接收协议；它的实际接收效果需由需求方拖放确认。

## 测试与检查

- `imageDragOffersReadableFileURLAlongsideOriginalImage`：真实 NSPasteboard 写入，验证有／无失效旧路径两种图片，NSURL 解出可读文件，文件字节与 PNG 一致，仍可读取原 PNG 和文件承诺；纯文本 NSTextView 可读取路径。
- `imageDragKeepsOriginalImageBytesAndExtension`：验证 TIFF 字节和承诺文件格式保留，拖出文本改为可读文件路径。
- 文本拖出精确内容、Finder 文件承诺和已有文件条目测试通过。
- `Scripts/check.sh`：Swift 136 项、Web 350 项通过；Debug 包构建与固定签名校验通过。

## 权限与验收

本次未重装应用、未重置任何权限。核对发现 `/Applications/DevBar.app` 是旧 ad-hoc 签名，当前构建使用固定 Apple Development 签名，两者身份不同；这可能影响权限沿用，不能承诺所有重装或签名变更都保留授权。图片拖拽修复本身未增加任何辅助功能调用。
