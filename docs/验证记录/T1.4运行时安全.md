## 1. 自检入口（可重复）

新增 `Sources/DevBar/Debug/WebSelfCheck.swift`，整个文件包在 `#if DEBUG` 里；`AppDelegate.applicationDidFinishLaunching` 末尾加了 3 行 `#if DEBUG` 调用；`ScreenStateStore.init` 里加了一段 `#if DEBUG` 分支（见下「状态目录隔离」）。Release 构建里三处都不存在（已确认 Release 二进制里没有 `devbar-selfcheck` 字符串），不改变 Release 的任何行为。

运行方式：

```bash
Scripts/build-app.sh debug
open -n -W build/DevBar.app --args --devbar-selfcheck /tmp/devbar-selfcheck.json
cat /tmp/devbar-selfcheck.json
```

- 自检**先等宿主重建完成、页面就绪**，再切到「工具」页并打开面板，然后在面板挂着的 WebView（`panel.webHost.webView`）里执行检查，约 5 秒后自动退出。先等就绪的原因见第 4.1 节。
- 结果 JSON 只记录检查项、状态、状态值和长度；自检只写入自己生成的随机标记文本，不读取也不记录用户内容。
- **状态取值**：`pass` 通过；`fail` 不通过；`unable` 前提不满足、无法完成检查（**不等于不通过**）；`observe` 只记录事实、不判通过与否。

**前提检查（第一项）**：页面就绪等待（最多 15 秒）的结果和「被测 WebView 已挂在面板上」都会检查并写进结果。页面未就绪时其余各项全部记为 `unable`；崩溃检查在崩溃前若被测 WebView 不在面板上，也记为 `unable`，不与「恢复失败」混同。

**状态目录隔离（R6 返工，替代原来的备份 / 恢复）**：

原做法是测试前备份、测试后恢复用户的 `~/Library/Application Support/DevBar/state/`。Codex 审核指出：备份读取失败被 `try?` 吞掉，恢复时又把「备份里没有的」一律删除，**会删掉测试前已存在的子目录**。现已改为：

- 带 `--devbar-selfcheck` 启动时，`ScreenStateStore` 改用独立的临时目录 `<系统临时目录>/devbar-selfcheck-<UUID>/state`（`SelfCheckEnvironment.stateDirectory`），**完全不读写用户状态目录**。
- 自检结束只删除这个临时测试目录本身。
- 自检代码里已没有任何备份、恢复、删除用户目录的逻辑。

隔离验证（2026-11-11）：在用户状态目录里临时放一个哨兵子目录 `__selfcheck_sentinel/keep.txt`，运行前后对用户目录做递归文件清单 + SHA-256 快照，中间连续运行自检两次：

| | 运行前 | 两次运行后 |
|---|---|---|
| `./__selfcheck_sentinel/` | 存在 | 存在 |
| `./__selfcheck_sentinel/keep.txt` | `b5f7e7d285029324…` | `b5f7e7d285029324…` |
| `./doc.json` | `a3117d48a7aa62ce…` | `a3117d48a7aa62ce…` |
| `./tools.json` | `b53af5460b1711ba…` | `b53af5460b1711ba…` |

`diff` 结果完全一致。两次自检都把状态写进了各自的临时测试目录（`doc.json 131B`、`tools.json 114B`），结束后系统临时目录里没有残留的 `devbar-selfcheck-*`。验证完已删除哨兵子目录。

**两次复测结果（2026-11-11，完全一致）**：前提 `pass`；第 1–6 项 `pass`；第 7 项 `fail`，且两次都完整复现「旧视图仍挂载」（见第 4 节）；激活状态观察项见 `面板焦点与输入法.md` 第 3 节。

## 3. 内容拦截规则的单独验证

在 App 的 WebView 里，外部请求同时会被 CSP 拦下，**分不清是哪一层拦的**。所以单独验证规则本身：

1. 从系统规则库取 App 启动时编译的那份规则（`WKContentRuleListStore.default()` 里标识为 `devbar-block-http` 的规则）——取到了，说明 App 确实编译并存入了这份规则。
2. 在本机 `127.0.0.1` 起一个最小 HTTP 服务，返回一张 1×1 PNG，并计数收到的请求。
3. 用两个**不带 CSP** 的 WebView 加载同一个 `http://127.0.0.1:<端口>/probe.png`：

| WebView | 图片结果 | 服务端收到的请求 |
|---|---|---|
| 不挂规则 | 加载成功 | 1 次 |
| 挂上 `devbar-block-http` | 加载失败 | **0 次**（请求根本没发出去） |

结论：**本机 HTTP 图片请求被拦截**——挂上规则后请求根本没有发出。**HTTPS 请求和图片以外的资源类型（fetch、脚本、样式、字体等）没有在这个对照实验里实测**；规则的匹配式是 `^https?://`，按规则本身应同样覆盖 HTTPS，但这一点属推断。

**没覆盖到的部分**：App 的 WebView 是否确实挂上了这份规则，`WKUserContentController` 没有公开接口可以读出已挂载的规则列表，只能靠代码审核确认（`WebHost.rebuild()` 中 `configuration.userContentController.add(ruleList)`）。另外 T1.4 审核记录提到的问题仍然存在：规则编译失败时只记日志、照常加载页面（失败开放），此时只剩 CSP 一层。

## 4. 不通过项：WebContent 崩溃后界面仍挂着旧的 WebView

做法：在「工具」写入标记文本并等前端保存（1.6 秒），读取 WebContent 进程号（Debug 下用私有键 `_webProcessIdentifier`），`kill -9` 结束它，然后观察。

| 观察项 | 结果 |
|---|---|
| 崩溃前，面板里挂着的是宿主的 WebView | 是 |
| 宿主是否重建（`generation` 1→2）并重新加载页面 | **是** |
| 新 WebView 里内容是否恢复（标记文本） | **是** |
| 崩溃后，面板里挂着的是新 WebView 吗 | **否** |
| 崩溃后，面板里是否仍挂着旧（已崩溃）的 WebView | **是** |
| 关闭再打开面板后，是否换成新 WebView | **否** |

结论：**宿主层面的重建和内容恢复是好的，但界面没有跟上**。用户看到的是已经崩溃的旧 WebView（空白或停止响应），而且重新开关面板也不能恢复。

可能原因（代码阅读，供修复者参考，未验证）：`PanelView` 用 `WebViewBox(host: webHost).id(webHost.generation)` 挂载 WebView，但 `WebHost` 不是可观察对象（没有 `@Observable`），`generation` 和 `webView` 变化时 SwiftUI 不会重新求值视图，`WebViewBox.updateNSView` 也不会被调用。

建议：由 R7 修复（本次验证不修改功能代码），修完后用本自检复测，第 7 项应当通过。

### 4.1 同一根因的启动时问题（R6 返工中发现）

返工后的自检最初是「一启动就打开面板」。连续两次运行，前提检查都是：页面就绪 `true`，但宿主当前的 WebView **没有挂在面板上**（`mountedAtStart = false`），**收起再打开面板后仍然没有**（`mountedAfterReopen = false`），`generation = 1`。

推断原因（代码阅读，未单独验证）：`WebHost.init` 先建一个占位 `WKWebView()`，随后异步 `start()` → `rebuild()` 换成真正的 WebView（`generation` 0→1）。如果面板在重建完成前就渲染了「工具」页，挂上去的是占位 WebView；由于第 4 节同样的原因（`WebHost` 不可观察），之后界面不会换成真正的 WebView。

影响：用户在 DevBar 刚启动、宿主还没重建完时就打开「工具」或「文稿」，可能看到一个永远空白的编辑区。日常使用中（启动后过一会儿再打开）没有触发，需求方 V1 实测也未遇到。

处理：自检改为先等就绪再打开面板，以便测到第 7 项真正的问题；这个启动时问题与第 4 节一并交 R7 修复，修复后应同时满足「启动立刻打开面板也挂上真正的 WebView」。
