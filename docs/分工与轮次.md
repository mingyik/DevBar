# DevBar 分工与轮次

> 生效日期：2026-11-10（T0.1 完成之后）。替代「一次一个任务、每个任务两方审核」的做法。
> 任务内容仍以 `docs/实现规格.md` §10 为准；本文只规定**谁做、哪一轮做、谁审、怎么合并**。

## 1. 三方分工

| 角色 | 负责 | 代码量 |
|---|---|---|
| **Grok** | **主力实现**：原生骨架、WebView 宿主、剪贴板界面、工具与文稿的界面接线、JSON 树、Mermaid 接入、截图长图、录屏 | 重 |
| **Codex** | **辅助实现**：设计变量管线、纯逻辑模块与大量测试用例、JSON 转换、Markdown 管线与排版 CSS、样张与配色核对、截图 / 录屏的验证原型；**审核 Claude 实现的部分** | 中 |
| **Claude** | **主审**：审核 Grok 和 Codex 的每一轮、负责合并进 `main`；少量实现：需要实测下结论的验证（V1–V3）和录屏状态机 | 轻 |

## 2. 审核规则

| 谁实现 | 谁审 | 加审（高风险任务） |
|---|---|---|
| Grok | Claude | R3 的 T1.4（WebView 安全）由 Codex 加审 |
| Codex | Claude | R4 的 T3.3（JSON 无损）由 Grok 加审 |
| Claude | Codex | — |

**结论只有两种**：
- **通过**：合并进 `main`。不影响功能和红线的小问题写进审核记录，**并入实现者的下一轮**，不单独返工。
- **打回**：违反 `AGENTS.md` 红线，或核心验收项没达成。实现者只修打回的点，审核者只复核这些点。

## 3. 工作目录与分支

三方各用一个独立的 git 工作目录（同一仓库的 `git worktree`，共享提交），互不干扰；`~/Desktop/DevBar`（`main`）只用来合并，**不在里面直接写代码**。

| 谁 | 工作目录 | 分支 |
|---|---|---|
| Grok | `~/Desktop/DevBar-grok` | `grok/rN` |
| Codex | `~/Desktop/DevBar-codex` | `codex/rN` |
| Claude | `~/Desktop/DevBar-claude` | `claude/rN` |

- `Reference/` 在各工作目录里是指向 `~/Desktop/DevBar/Reference` 的符号链接（已被 `.gitignore` 忽略）。
- 每轮开始时，在自己的工作目录里执行 `git switch -c <名>/rN main`，从最新 `main` 拉新分支（R1 的分支已建好）。
- 每轮结束：在自己的分支上提交，回报里写明分支名和提交号。**不要自己合并进 `main`**。
- 合并由 Claude 在审核通过后执行（`git merge --no-ff <分支>`），并把审核记录单独提交。
- 同一轮里并行的两方**不改同一批文件**（见下表括号里的目录）。确需改公共文件（如 `Package.swift`、`Web/package.json`、`Scripts/check.sh`、`AGENTS.md`）时，在回报里单独列出，由 Claude 合并时处理冲突。

## 5. 回报

仍按 `docs/实现规格.md` §11 的格式，**一轮一份回报**，在开头写明：轮次、实现者、分支名、提交号、本轮包含的任务编号。每个任务的验收证据分开列。
